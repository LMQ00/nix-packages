# Repository Guidelines

## Project Overview

Personal Nix package collection managed as a single-input Flake. It exposes nine packaged applications/libraries through both a reusable overlay and `packages.<system>` outputs; `musicdl` is the default package.

## Architecture & Data Flow

**Architecture pattern:** declarative Nix derivations, one package per directory.

```text
flake.lock → nixpkgs-unstable
flake.nix → overlay (callPackage ./pkgs/<name>)
          → packages.<system> (re-export overlay packages)
          → devShells.<system>.default
nix build/run → evaluated derivation → Nix store output / wrapped executable
```

- `flake.nix` imports pinned `nixpkgs`, enables the project overlay, and applies `allowUnfree` plus the narrowly scoped `libsoup-2.74.3` insecure-package exception.
- Every package is registered manually twice in `flake.nix`: once in `overlays.default`, then again under `packages`. Keep both lists synchronized.
- Package definitions fetch immutable upstream sources with a fixed `hash`, build or unpack them, then wrap runtime dependencies when necessary.
- Common implementation families:
  - Python: `buildPythonApplication` or `buildPythonPackage`, `pyproject = true`, `fetchPypi`/`fetchFromGitHub`.
  - Node: `pnpm.configHook`/`pnpm.fetchDeps`, then `makeWrapper` for the Node CLI.
  - Prebuilt desktop software: `.deb` extraction with `autoPatchelfHook`, AppImage wrapping, Wine-prefix construction, or platform-conditional bundle installation.

## Key Directories

- `pkgs/<package>/default.nix` — one self-contained package derivation per package.
- `flake.nix` — flake input, supported systems, overlay registration, package exports, and development shell.
- `flake.lock` — pinned `nixpkgs` revision; generated by Nix, never edited by hand.
- `README.md` — public package table, installation examples, licenses, and version-update notes.
- `FLAKE_LOCK.md` — lockfile maintenance instructions.

There are no repository `src/`, `tests/`, `scripts/`, or CI-workflow directories.

## Development Commands

Run commands from the repository root:

```bash
# Enter a shell containing nixpkgs-fmt and nil
nix develop

# Build one package; canonical command for packages that require unfree evaluation
NIXPKGS_ALLOW_UNFREE=1 nix build .#<package> --impure

# Run a local package
nix run .#<package> --impure

# Update the locked nixpkgs input
nix flake update nixpkgs

# Update every flake input
nix flake update

# Regenerate the lockfile when required
nix flake lock
```

Format Nix files with `nixpkgs-fmt` from `nix develop`, for example:

```bash
nixpkgs-fmt pkgs/musicdl/default.nix flake.nix
```

Do **not** rely on `nix fmt`: `flake.nix` has no `formatter.<system>` output.

For a source update, set the package `hash` to `lib.fakeHash`, build the affected package, then replace it with Nix's reported hash.

## Code Conventions & Common Patterns

- Keep package names and directories aligned: `pkgs/foo/default.nix` is exported as `foo`.
- Use a Nix argument set and only request dependencies used by the derivation. Prefer standard nixpkgs fetchers (`fetchPypi`, `fetchFromGitHub`, `fetchurl`) and fixed hashes.
- Define `pname` and `version` near the top; use a `meta = with lib; { ... };` block with at least description, homepage, license, maintainers, and `mainProgram` when executable.
- Separate `nativeBuildInputs`, `buildInputs`, and language-specific dependencies. Prefer standard hooks (`autoPatchelfHook`, `makeWrapper`, `wrapProgram`, Python hooks) over ad-hoc environment mutation.
- Wrappers are the established boundary for runtime-only dependencies, PATH/RPATH fixes, and per-user state such as Wine prefixes. Keep wrapper behavior explicit and minimal.
- Existing packages commonly set `doCheck = false` because upstream tests are unsuitable for the Nix sandbox. Do not add a disabled check without a concrete reason; add a viable check when the upstream package supports one.
- Error/update flow: let Nix report fixed-output hash mismatches; update the declared hash rather than bypassing verification.
- This repository has no application-level async, dependency-injection, or state-management framework. Do not introduce such patterns into package definitions; use declarative derivation attributes and minimal shell wrappers instead.
- Avoid FHS environments (`buildFHSUserEnv` or `buildFHSEnv`) unless the user explicitly approves. `pkgs/sunlogin/default.nix` is an existing compatibility exception, not a general pattern.
- Keep builds atomic and reproducible. Do not add network access at build time beyond declared fixed-output fetches.

## Important Files

- `flake.nix` — source of truth for supported systems (`x86_64-linux`, `aarch64-linux`, `x86_64-darwin`, `aarch64-darwin`) and all exports.
- `pkgs/musicdl/default.nix` — default package; representative Python application plus runtime wrapper.
- `pkgs/sub-store/default.nix` — representative Node/pnpm package.
- `pkgs/sunlogin/default.nix` — complex proprietary `.deb` package and the existing FHS compatibility exception.
- `pkgs/wecom-wine/default.nix` — Wine prefix template and first-run copy behavior.
- `pkgs/astudio/default.nix` — platform-specific AppImage/macOS bundle packaging.
- `README.md` — update its package table and license information whenever a package changes.

## Runtime/Tooling Preferences

- Use **Nix Flakes** with the repository's pinned `nixpkgs-unstable`; Nix is the package manager and build runtime.
- The flake targets four systems, but individual packages can impose stricter platform support. Preserve or declare platform restrictions in `meta.platforms` where applicable.
- `nix develop` provides `nixpkgs-fmt` and the `nil` Nix language server. No Node, Python, pnpm, or other host-language runtime is a repository-wide prerequisite; derivations supply what they need.
- Unfree packages are supported through the flake configuration. Use the canonical `NIXPKGS_ALLOW_UNFREE=1 ... --impure` command when required by the target package or caller configuration.
- `libsoup-2.74.3` is deliberately permitted as insecure for `sunlogin`; do not broaden that exception.
- Do not edit `flake.lock` manually. Regenerate/update it with Nix and commit the result when inputs change.

## Testing & QA

- No test suite, `checks` output, CI workflow, linter, coverage tool, or pre-commit configuration exists.
- `nix flake check` has no repository checks to run. The focused verification for a derivation change is a successful build of that package:

  ```bash
  NIXPKGS_ALLOW_UNFREE=1 nix build .#<package> --impure
  ```

- For changes affecting startup or wrappers, also smoke-test the intended executable with `nix run .#<package> --impure` when it is safe and practical.
- After test builds, clean temporary/unreferenced Nix build outputs as required by repository policy:

  ```bash
  nix-store --gc
  ```

## Change Checklist

When adding or changing a package:

1. Update `pkgs/<package>/default.nix` and verify its focused build.
2. Add or update the package in both the overlay and `packages` export lists in `flake.nix`.
3. Update `README.md` package and license information; update any NixOS configuration only when that package is installed there.
4. Format touched Nix files, clean after test builds, and provide a commit message rather than creating a commit automatically.
